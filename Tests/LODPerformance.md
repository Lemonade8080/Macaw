# 사과 50,000개 LOD 조정 결과

2026-10-01, NVIDIA GeForce RTX 4060, Release x64, 1920×1080.

## 적용 설정

`Asset/FLODSettings.h`에 5단계를 적용했다. 화면 크기는 바운딩 구의 투영 지름 / 뷰포트 높이이며, 경계의 ±8% 구간에서 인접한 두 LOD를 디더링으로 전환한다.

| 단계 | 화면 크기 경계 | 목표 삼각형 비율 | apple 실제 삼각형 | bitten apple 실제 삼각형 |
|---|---:|---:|---:|---:|
| LOD0 | 0.50 | 100% | 2,104 | 2,014 |
| LOD1 | 0.25 | 50% | 1,052 | 1,006 |
| LOD2 | 0.12 | 22% | 462 | 442 |
| LOD3 | 0.05 | 8.5% | 178 | 170 |
| LOD4 | 0 | 3% | 78 | 60 |

예를 들어 화면 높이의 5% 경계에서 LOD3 → LOD4 전환이 일어난다. 실제 전환 범위는 4.6%~5.4%다. 최하위 단계의 0은 컬링 거리가 아니라 마지막 단계라는 뜻이다.

서브메시 재질 경계, UV/Normal 경계, 기하 유효성을 유지하므로 목표 비율보다 많은 삼각형이 남을 수 있다. 이 사과들은 더 낮은 비율을 요청해도 78/60개 아래로 줄지 않았다. 이를 위한 중복 단계는 추가하지 않았다.

화면 지름 1.5픽셀부터 서서히 지우고, 0.75픽셀 이하에서는 CPU 그리기 목록에서 제외한다. 선택된 물체, 하늘, LOD가 꺼진 뷰는 이 컬링에서 제외된다. 뷰포트 높이를 큐 캐시 키에 추가해 창 크기 변경 시에도 픽셀 기준이 갱신된다.

`Render/RenderConfig.h`의 기존 인스턴싱 경로도 활성화했다. 같은 메시/재질/LOD를 배치 단위로 그린다. 전환 가중치는 기존 16바이트 draw record의 패딩을 사용하므로 GPU 레코드 크기는 증가하지 않는다. 카메라와 장면이 정지하면 기존 큐 캐시를 재사용하며 시간에 따라 바뀌는 노이즈나 타이머는 없다.

## 측정 방법과 한계

`Tests/LODBenchmark.cpp`는 `scenes/Default.scene`의 50,000개 배치와 두 사과 메시/텍스처를 읽고, 실제 `FRenderScene`, `FRenderQueue`, `FFrameResource`, `FMeshRenderer`, TexturedBase 셰이더로 오프스크린 렌더링한다. 벤치마크용 방향광 하나를 사용한다. 각 경로에서 20프레임 준비 후 80프레임의 평균을 기록했다.

- 경로 0: 저장된 카메라 위치에서 X/Y 방향으로 이동.
- 경로 1: 사과 배열 내부의 근접 이동. 카메라가 물체 내부를 지나갈 수도 있는 부담이 큰 경로.
- 경로 2: 같은 카메라 방향으로 후퇴. 먼 장면 측정을 위해 이 경로만 far clip을 2,000으로 설정.

GPU 시간은 D3D11 timestamp query로 측정한다. 프레임 시간은 큐 생성, GPU 자료 업로드, 그리기 제출, GPU 완료 대기를 포함한다. 각 프레임 GPU 완료를 기다리는 직렬 벤치마크이므로 실제 에디터의 프레임 파이프라이닝과 다르다. UI, 월드 Tick, 화면 표시, VSync 비용은 포함하지 않는다. `render_only_fps`를 실제 에디터 FPS로 해석하면 안 된다.

## 기존 설정과 최종 설정

| 경로 | 기존 GPU ms | 최종 GPU ms | 기존 렌더 프레임 ms | 최종 렌더 프레임 ms | 기존 삼각형/프레임 | 최종 삼각형/프레임 | 기존 draw calls | 최종 draw calls |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 기본 이동 | 1.972 | 1.068 | 2.699 | 1.785 | 3,242,820 | 1,380,210 | 15,820.7 | 5 |
| 근접 이동 | 1.790 | 1.804 | 2.433 | 2.498 | 3,022,040 | 2,760,360 | 12,084.1 | 9.64 |
| 원거리 | 0.602 | 0.250 | 1.020 | 0.713 | 1,297,760 | 436,524 | 6,331.5 | 2 |

기본 이동 GPU 시간은 약 46%, 렌더 프레임 시간은 약 34% 줄었다. 근접 이동은 반복 측정에서 2.42~2.50ms로 기존과 비슷했다. 모든 카메라 위치에서 FPS가 향상된다는 결과는 아니다. 원거리 경로는 아직 대부분 1.5픽셀보다 커서, 해당 개선은 주로 낮은 LOD와 인스턴싱의 효과다. 서브픽셀 컬링 자체는 별도의 생산 렌더 큐 테스트로 확인했다.

## 후보 비교

| 후보 | ScreenSize 배열 | TargetRatio 배열 | 전환 반폭 | 기본 이동 GPU ms | 근접 GPU ms | 원거리 GPU ms |
|---|---|---|---:|---:|---:|---:|
| 기존 4단계 | .5, .25, .12, .06 | 1, .5, .3, .1 | 즉시 교체 | 1.972 | 1.790 | .602 |
| 7단계 | .35, .18, .085, .04, .018, .0075, 0 | 1, .55, .28, .13, .06, .025, .01 | 12% | 2.126 | 3.350 | .234 |
| 6단계 | .5, .25, .12, .06, .025, 0 | 1, .5, .25, .1, .045, .02 | 8% | 1.228 | 1.769 | .255 |
| 선택한 5단계 | .5, .25, .12, .05, 0 | 1, .5, .22, .085, .03 | 8% | 1.068 | 1.804 | .250 |

새 후보들은 모두 인스턴싱과 디더 전환을 사용했다. 7단계는 가까운 거리의 삼각형과 두 LOD를 함께 그리는 비용이 커졌고, 최하위 두 단계는 실제 삼각형 수도 같았다. 5단계가 이 장면의 기본 이동 성능과 전환 비용 면에서 가장 나았다. 모든 가능한 설정을 탐색한 절대 최적값은 아니다.

디더링은 알파 블렌딩 없이 두 메시의 픽셀을 서로 보완해 순간 교체를 완화한다. TAA가 없는 현재 렌더러에서는 전환 중 미세한 점무늬가 보일 수 있으며, 카메라가 한 프레임에 전체 전환 구간을 건너뛰는 경우까지 완전한 무팝핑을 보장하지는 않는다. 생성된 장면 캡처를 확인했고, GPU 테스트로 전환의 픽셀 누락과 완전 소멸 지점을 검증했다. 새 단계 하나만큼 로딩 시 생성 시간과 LOD GPU 버퍼 메모리는 증가한다.

## 재현 및 검증

프로젝트 루트에서 Release x64 솔루션을 빌드한 뒤 실행한다. 스크립트는 vswhere로 Visual Studio를 찾는다.

```bat
Scripts\RunLODBenchmark.cmd current 1080
Scripts\RunLODSelectionTests.cmd
```

측정 CSV와 장면 PNG는 `Build/LODResults/`에 저장된다. 첫 번째 인자는 결과 파일의 이름표이며 설정 프리셋을 바꾸지 않는다. 기존 상태 재현에는 수정 전 소스/셰이더/라이브러리가 필요하다.

통과한 검증:

- 전체 Release x64 솔루션 빌드.
- 기존 `Build/RunLODCollapseChecks.cmd`: SubMesh 재질/범위, UV 및 Normal 경계, 잘못된 구간 거부.
- `RunLODSelectionTests.cmd`: 모든 LOD 경계의 연속 가중치, 누락된 단계 대체, 픽셀 컬링, 선택 예외.
- 생산 렌더 큐의 전환 시 두 배치와 반대 부호의 가중치, 같은 객체/재질 연결, 창 크기 변경 시 캐시 무효화, LOD 비활성화.
- 변경된 모든 메시 VS/PS 및 Outline GS 컴파일.
- WARP GPU readback: 두 전환 패스의 상보적인 픽셀 커버리지, 전환 비율, 완전 소멸 시 픽셀 미출력.
